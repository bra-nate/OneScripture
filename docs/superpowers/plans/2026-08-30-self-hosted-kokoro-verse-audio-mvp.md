# OneScripture Self-Hosted Kokoro Verse Audio MVP

**Date:** 2026-08-30
**Status:** Approved direction; ready for implementation planning
**Project:** OneScripture
**Depends on:** Existing Next.js application, Supabase authentication/persistence work, an approved scripture-text source, and [`2026-08-30-onescripture-vibrant-audio-design-system.md`](../specs/2026-08-30-onescripture-vibrant-audio-design-system.md)

> **Phase 1 deployment amendment (2026-08-31):** The existing hosted Supabase
> project is the active Auth and database platform for the MVP. Do not start a
> local Supabase stack or provision a replacement VPS unless that deployment
> change is approved separately. The self-hosting design below remains a future
> migration option; it is not the current Phase 1 execution path.

## 1. Objective

Build an MVP in which a user can select one verse, a verse range, a complete chapter, or several unrelated scriptures; have any missing narration generated by a self-hosted Kokoro worker; and play the resulting ordered selection once or continuously on a loop.

The system will generate each verse only once per translation, voice, model version, and source-text version. Subsequent selections will reuse those verse recordings instead of synthesizing the same text again.

## 2. Decisions already made

| Area | Decision | Reason |
| --- | --- | --- |
| TTS model | Kokoro-82M | Open-weight, Apache 2.0, small enough to self-host, and no per-character API fee |
| MVP voices | `af_heart` (female) and `am_michael` (male) | Gives users a clear female/male narration choice while keeping the asset catalogue bounded |
| Backend | Self-hosted Supabase | Preserves the existing Supabase Auth, SSR helpers, Postgres schema, and RLS work |
| Hosting | One VPS initially | Keeps the application, database, storage, and worker under our control |
| File storage | Self-hosted Supabase Storage using the VPS filesystem | Retains Supabase Storage metadata and access policies without requiring S3 |
| Audio unit | One canonical asset per verse | Arbitrary user selections can be assembled without generating every possible combination |
| Generation strategy | Lazy and reusable | Generate missing verses on demand, then reuse them for all later users |
| Playback strategy | Ordered verse playlist | Supports one verse, chapters, ranges, and unrelated references with one player model |
| Visual system | Chromatic scripture rooms | Gives each major route a deterministic color atmosphere while keeping navigation, controls, and the player coherent |
| Texture | Subtle static grain | Softens saturated page colors without adding animated noise or visual clutter |
| Browser storage | Preferences only | `localStorage` will hold loop, speed, volume, and voice settings—not audio bytes |
| MVP download behavior | No download button | The first release focuses on controlled playback; downloads require a separate rights decision |
| Random playback | Post-MVP | It will reuse the same verse catalogue after the core generation and playlist flow is stable |

## 3. Scope

### 3.1 MVP includes

- One approved English scripture translation.
- Two approved Kokoro voices: one female and one male.
- Selection of:
  - one verse;
  - a contiguous verse range;
  - one complete chapter; or
  - multiple unrelated verse references.
- Normalization of every selection into an ordered list of canonical verses.
- Lookup and reuse of previously generated verse audio.
- Background generation of missing verse audio.
- Progressive readiness reporting while a selection is prepared.
- Ordered playback of verse audio.
- Play-once and continuous-loop modes.
- Playback-speed controls that let users slow down or speed up the reading, plus volume controls.
- Preference persistence after a page refresh.
- Deterministic route themes, accessible foreground pairings, and subtle static grain as defined by the vibrant audio design system.
- Self-hosted database, authentication, storage, and generation.
- Backups, basic monitoring, rate limiting, and failure recovery.

### 3.2 Explicitly excluded from the MVP

- User-supplied arbitrary text.
- Voice cloning.
- Twi or Ga synthesis.
- Multiple translations or voices beyond the approved female/male pair.
- Permanent offline audio storage in the browser.
- A visible audio-download feature.
- Server-side creation of combined selection MP3s.
- Random scripture sessions.
- Full playlist management changes beyond what is necessary for playback.
- Mobile applications.

Recommended starting capacity:

- 4 CPU cores;
- 8 GB RAM;
- 160 GB SSD;
- sufficient monthly bandwidth for long-running audio;
- Ubuntu LTS or another supported Linux distribution.

The Kokoro worker must have its own memory and CPU limits so generation cannot make the web application or database unavailable.

## 6. Storage design

Supabase Storage will use its local filesystem backend through a persistent VPS bind mount.

Bucket:

```text
scripture-audio
```

Proposed object path:

```text
<translation>/<model-version>/<voice>/<book>/<chapter>/<verse>.mp3
```

Example:

```text
KJV/kokoro-82m-v1/voice-1/JHN/003/016.mp3
```

Storage requirements:

- MP3 is the MVP delivery format.
- WAV is temporary and must be deleted after successful conversion.
- Audio files are private by default.
- Playback uses short-lived signed URLs.
- HTTP range requests must work so seeking does not require reloading the entire file.
- Cache headers should allow the browser to reuse audio during looping while respecting signed-URL behavior.
- The worker uploads through the Storage API so Storage metadata remains consistent; it must not write directly into the bind-mounted bucket directory.

## 7. Selection normalization

Every accepted input is converted to the same internal structure:

```ts
type NormalizedSelection = {
  translationId: string;
  voiceId: string;
  verses: Array<{
    bookId: string;
    chapter: number;
    verse: number;
  }>;
};
```

Examples:

```text
John 3:16
→ JHN 3:16

John 3:16-18
→ JHN 3:16, JHN 3:17, JHN 3:18

John 3
→ every canonical verse in John 3

John 3:16 + Psalm 23:1 + Romans 8:28
→ JHN 3:16, PSA 23:1, ROM 8:28
```

Rules:

- Preserve the order entered by the user.
- Reject unknown books, chapters, and verses.
- Reject duplicate verses or remove them deterministically; the MVP will remove duplicates while preserving the first occurrence.
- Enforce a maximum number of verses per request.
- Never accept raw text for synthesis.
- Load synthesis text only from `scripture_verses`.

## 8. Kokoro generation worker

The worker will be a Python service separate from the Next.js process.

Responsibilities:

1. Load Kokoro once at startup.
2. Poll or subscribe for queued jobs.
3. Claim one job atomically.
4. Load the canonical verse text from the database.
5. Verify translation narration rights.
6. Normalize text for speech without changing canonical stored text.
7. Generate WAV audio.
8. Validate that the output is nonempty and playable.
9. Normalize loudness and convert to MP3 with FFmpeg.
10. Upload the MP3 through Supabase Storage.
11. Update asset duration and status.
12. Retry transient failures with backoff.
13. Permanently fail invalid or repeatedly unsuccessful jobs.
14. Delete temporary local files in both success and failure paths.

Worker safety:

- Start with concurrency `1`.
- Use a deterministic worker identifier.
- Recover abandoned locks after a defined timeout.
- Limit retries.
- Cap input length even though input is canonical.
- Record model and voice versions with every output.
- Do not support voice cloning.
- Do not expose the worker directly to the public internet.

## 9. Application API

### 9.1 Create or resolve a selection

```text
POST /api/audio/selections
```

Request:

```json
{
  "translationId": "KJV",
  "voiceId": "voice-1",
  "references": ["John 3:16", "Psalm 23:1", "Romans 8:28"]
}
```

Behavior:

1. Validate and normalize references.
2. Confirm the translation permits audio generation and streaming.
3. Resolve or create an `audio_verse_assets` row for each verse.
4. Create jobs only for missing assets.
5. Create the ordered selection and items.
6. Return selection identity and readiness counts.

Response:

```json
{
  "selectionId": "uuid",
  "status": "preparing",
  "ready": 2,
  "total": 3
}
```

### 9.2 Read selection status and playable items

```text
GET /api/audio/selections/[selectionId]
```

Preparing response:

```json
{
  "status": "preparing",
  "ready": 12,
  "total": 36,
  "items": []
}
```

Ready response:

```json
{
  "status": "ready",
  "ready": 36,
  "total": 36,
  "items": [
    {
      "id": "uuid",
      "position": 0,
      "reference": "John 3:1",
      "url": "signed-url"
    }
  ]
}
```

The first MVP may wait until every item is ready before returning playable items. Progressive playback can then be added without changing the database model or route shape.

### 9.3 Retry failed generation

```text
POST /api/audio/selections/[selectionId]/retry
```

Only failed assets that have not exhausted their retry allowance will be queued again.

## 10. Player behavior

The current single-source player will become an ordered sequence player.

Required state:

```text
idle
preparing
ready
playing
paused
completed
error
```

Required controls:

- Play and pause.
- Previous and next verse.
- Female/male voice selector.
- Play once.
- Loop the complete selection.
- Playback speed from `0.75×` to `1.5×` in `0.25×` steps.
- Volume.
- Visible current verse reference.
- Generation progress while preparing.
- Retry when generation fails.

Sequence rules:

- Preload the next verse before the current verse finishes.
- Advance automatically when a verse ends.
- Insert a consistent, short pause between verses if needed.
- In `once` mode, stop after the final verse.
- In `loop` mode, return to the first verse after the final verse.
- Apply playback-speed changes immediately without generating a new audio asset.
- Resolve a separate reusable asset when the user changes voice.
- Refresh expired signed URLs without losing the current position.
- Surface failed verses instead of silently skipping them.

Preferences stored in `localStorage`:

```json
{
  "playbackMode": "loop",
  "playbackSpeed": 1,
  "volume": 0.8,
  "voiceId": "voice-1"
}
```

Audio bytes must not be stored in `localStorage`.

### 10.1 Visual behavior

Player and generation UI must follow the vibrant audio design system:

- passage playback uses the Electric Purple page theme for the first MVP;
- the player remains a stable near-ink surface across page themes;
- the active timeline inherits the page theme;
- preparing, ready, warning, and failed states use semantic colors plus labels or icons;
- the player remains legible over saturated and gradient page backgrounds;
- grain is static, subtle, and applied to the page canvas rather than individual controls;
- reduced-motion users receive equivalent state feedback without animated transitions.

## 13. Post-MVP roadmap

### 13.1 Progressive playback

Allow playback to begin once the first few verses are ready while remaining verses continue generating.

### 13.2 Random scripture sessions

Build shuffled queues from curated pools, books, favourites, or themes. Random mode will resolve the same canonical verse assets and prefetch the next items.

### 13.3 Offline mode

Use Cache Storage or IndexedDB only for translations whose rights explicitly permit offline copies. Provide storage usage and removal controls.

### 13.4 Combined selection downloads

If rights permit downloads, concatenate cached verse MP3s with FFmpeg, store the combined result by a deterministic selection hash, and reuse it for identical requests. Kokoro must not run again for combination.

### 13.5 Additional voices and translations

Add a translation or any voice beyond the initial female/male pair only after its text, model, voice, generation, streaming, caching, and download rights have been recorded. Twi and Ga require a separate model-quality and licensing investigation.

### 13.6 Continuous chapter narration

Popular chapters may receive separately generated continuous-narration assets if verse transitions sound too fragmented. These are enhancements and do not replace canonical verse assets.

## 14. Security requirements

- Never accept arbitrary synthesis text from a browser.
- Never expose the Supabase service-role key to client code.
- Never expose the Kokoro worker publicly.
- Enforce authentication or anonymous rate limits on selection creation.
- Limit verses per selection and outstanding jobs per user/IP.
- Use private audio storage and signed URLs for the MVP.
- Validate object paths and MIME types server-side.
- Run containers as non-root where practical.
- Keep Supabase, the operating system, Docker images, Kokoro dependencies, and FFmpeg patched.
- Encrypt sensitive configuration and protect VPS administrative access with SSH keys.

## 15. Backup and recovery requirements

Back up separately:

1. PostgreSQL data and roles.
2. Supabase Storage files.
3. Supabase and application environment configuration.
4. Deployment manifests and version pins.

At least one backup copy must live outside the production VPS. Audio files are reproducible, but accounts, playlists, favourites, rights records, and generation metadata are not. A backup is not accepted until a restore has been tested.

## 17. MVP acceptance criteria

The MVP is complete when all of the following are true:

1. One approved translation and the approved female/male voice pair are configured with documented rights.
2. One verse, a range, a chapter, and several unrelated verses normalize correctly.
3. Missing verses are queued and generated by self-hosted Kokoro.
4. Each canonical verse is generated at most once for the same text/model/voice version.
5. Generated MP3s are stored on the VPS through self-hosted Supabase Storage.
6. Previously generated verses are reused across users and selections.
7. The player plays the selection in order and supports play-once and loop modes.
8. A user can choose the approved female or male voice and adjust reading speed from `0.75×` to `1.5×`.
9. Player preferences survive refresh without storing audio in `localStorage`.
10. The legacy arbitrary audio-download proxy is no longer part of the product flow.
11. The vibrant design system is applied with deterministic route themes, accessible contrast, stable player chrome, and subtle static grain.
12. Rate limits, retries, monitoring, external backups, and a tested restore procedure are in place.

## 18. Principal risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Verse-by-verse narration sounds fragmented | Consistent voice/settings, controlled pauses, next-item preloading, and later continuous chapter assets |
| CPU generation slows the website | Separate worker, concurrency limits, container resource limits, and durable queue |
| First request for a chapter takes too long | Cache every verse permanently, show progress, and add progressive playback after core MVP |
| Duplicate jobs waste compute | Unique asset constraint, one-active-job constraint, and atomic job claiming |
| VPS disk fills | MP3 delivery assets, temporary WAV cleanup, disk monitoring, retention rules, and capacity planning |
| VPS loss destroys the service | Automated off-server database and storage backups plus restore drills |
| Model or voice changes alter output | Pin versions and include model/voice/text versions in asset identity |
| Translation or voice rights are unclear | Rights gate before enabling display, generation, streaming, caching, or downloads |
| Signed URLs expire mid-session | Refresh URLs through the selection endpoint without resetting playback state |
| Saturated route colors become chaotic or inaccessible | Use deterministic named themes, semantic foreground tokens, stable player chrome, measured contrast, and restrained grain |
| Grain hurts rendering performance or readability | Use one small local static texture, cap opacity at 0.04, avoid animation, and test mobile rendering |
| Browser suspends overnight playback | Test target browsers, document platform limitations, and consider PWA/mobile work after MVP |
